# mdview v1.3 Rendering Engine Design

**Status:** Implemented; qualification and maintainer review in progress
**Date:** 2026-10-05  
**Planning baseline:** `2701d9c24f65cf2f3b5007bc017e5ac5591dff4a` (`release: v1.2.5`)  
**Target:** v1.3.0  
**Implementation:** Implemented on the 1.3.0 branch; pending packaged-app qualification and maintainer review

## Product intent

v1.3 turns mdview's preview from a collection of rendering helpers into a deliberate Markdown rendering system. The goal is not to add vaults, backlinks, graph view, or global workspace search yet. The goal is to make one opened Markdown document render and navigate with the completeness and polish users expect from mature Markdown tools, while preserving mdview's local-first and untrusted-content security model.

The release promise is:

> Open a real-world Markdown document and mdview should render it correctly, safely, beautifully, and predictably.

This release is also the architectural base for later workspace features. Headings, links, resources, and render metadata must become structured data rather than ad-hoc DOM behavior so future workspace indexing does not require another renderer rewrite.

## What v1.2.5 already gives us

The v1.2.5 baseline already contains more than the old roadmap suggests:

- Marked with GFM and single-line-break behavior.
- DOMPurify sanitization and a documented preview sandbox.
- Mermaid rendering with strict mode, source preflight, and SVG sanitization.
- KaTeX inline and block math with `trust: false`.
- Obsidian/GitHub-style callout syntax for the five GitHub alert types.
- Wikilink tokenization and app-level wikilink navigation.
- Interactive task-list toggles.
- Local-image authorization through Rust/Tauri before `convertFileSrc`.
- Attachment paste/drop handling.
- Multi-tab opening and pending heading navigation.

v1.3 must reuse these capabilities. It must not implement parallel renderers or duplicate path-resolution logic.

## Competitor benchmark

### Obsidian

Obsidian's reading experience is strong because individual notes have rich primitives: an Outline core plugin, internal heading links, local image/file embeds, callouts with aliases/nesting/folding, syntax-highlighted code, footnotes, math, and Mermaid. Its graph view is a separate knowledge-navigation capability, not a prerequisite for high-quality document rendering.

Relevant references:

- https://obsidian.md/help/plugins/outline
- https://obsidian.md/help/syntax
- https://obsidian.md/help/callouts
- https://obsidian.md/help/embeds

### GitHub Markdown

GitHub sets useful expectations for repository documentation: relative links and images, deterministic heading anchors and an outline, tables, syntax-highlighted code fences, task lists, alerts, footnotes, math, and Mermaid diagrams.

Relevant references:

- https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax
- https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting
- https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes

### Typora

Typora is a useful benchmark for local-document ergonomics. It resolves images relative to the current Markdown file, supports `./` and `../` paths, handles escaped/unescaped paths, drag/drop and paste workflows, local file links, an outline, math, code fences, diagrams, tables, footnotes, front matter, and GitHub-style alerts.

Relevant references:

- https://support.typora.io/Images/
- https://support.typora.io/

## Approaches considered

### A. Modularize the current stack — selected

Keep Marked, DOMPurify, KaTeX, Mermaid, React, and the Tauri/Rust trust boundary. Create a `src/rendering/` subsystem with per-render state, structured metadata, explicit sanitizer policy, resource classification, and isolated DOM enhancers.

**Why it wins**

- Preserves the v1.2.5 security work.
- Smallest migration risk.
- Marked is designed for extension.
- Lets us improve one rendering primitive at a time with TDD.
- Avoids rewriting working task-list, wikilink, math, and Mermaid behavior.
- Provides enough structure for later workspace indexing.

### B. Migrate to unified/remark/rehype now — rejected for v1.3

An AST-first unified pipeline would be powerful, but it would replace the parser and extension surface at the same time we are trying to stabilize user-visible rendering. The migration would require re-proving sanitization, raw-HTML behavior, task editing, math, Mermaid, links, and resource policies with little immediate user benefit.

Revisit only if future workspace features require transforms that are materially painful with Marked tokens.

### C. Replace HTML rendering with a React-node/MDX renderer — rejected

This would make interactive render nodes easier, but MDX/React rendering expands the trust boundary and moves mdview away from "untrusted Markdown is data." It is unnecessary for v1.3 and conflicts with the current sanitized-HTML security model.

## Selected rendering architecture

```text
Markdown source
    |
    v
createRenderSession()
    |
    +--> Marked parser + mdview extensions
    |      - headings/IDs
    |      - callouts
    |      - wikilinks
    |      - math
    |      - highlights
    |      - footnotes
    |      - task metadata
    |
    v
untrusted HTML + render metadata
    |
    v
security sanitizer
    |
    +--> safe HTML
    +--> outline/headings
    +--> resource references
    +--> diagnostics
    |
    v
Preview
    |
    +--> authorize/resolve local image assets through Tauri
    +--> render + sanitize Mermaid SVG
    +--> enhance code blocks
    +--> attach navigation/task interactions
    +--> image lightbox/error UX
    |
    v
Reader / Split view
```

### Core contract

The renderer should return a structured result rather than only an HTML string.

```ts
export type HeadingEntry = {
  id: string;
  text: string;
  level: 1 | 2 | 3 | 4 | 5 | 6;
  ordinal: number;
};

export type RenderResource = {
  kind: "image" | "local-link" | "remote-link";
  raw: string;
};

export type RenderDiagnostic = {
  level: "info" | "warning" | "error";
  code: string;
  message: string;
};

export type RenderResult = {
  html: string;
  headings: HeadingEntry[];
  resources: RenderResource[];
  diagnostics: RenderDiagnostic[];
};
```

The exact type may evolve during implementation, but these responsibilities are fixed: one parse produces safe preview HTML and the metadata the surrounding UI needs.

### Per-render parser state

The current math renderer relies on module-level mutable state. v1.3 should create a fresh render session/parser for each render so heading slug state, math placeholders, metadata collection, and extension state cannot leak between documents or concurrent renders.

The primary API becomes conceptually:

```ts
renderMarkdownDocument(markdown, options): Promise<RenderResult>
```

A temporary `renderMarkdown()` compatibility wrapper may remain while tests/components migrate, then should be removed before v1.3 is cut.

## Heading IDs and Outline

Heading identity becomes a renderer concern, not a post-render DOM guess.

Requirements:

- Every rendered H1-H6 gets a deterministic unique `id`.
- Duplicate headings receive deterministic suffixes.
- Renderer returns heading text, level, ID, and order.
- Same-document `#fragment` links resolve against those IDs.
- Cross-document `other.md#Heading` opens/focuses the document and navigates after its render completes.
- Human heading text remains a fallback for existing wikilink navigation.
- Navigation searches only within the active preview root, never the global document.

### Outline UI

The Outline is intentionally quiet:

- Closed by default for existing users.
- One toolbar/edge control toggles it.
- Desktop: docked left panel with a compact 220–280 px width.
- Narrow windows: overlay drawer rather than crushing source/preview panes.
- Nested indentation follows heading levels.
- Current section is highlighted using `IntersectionObserver`.
- Clicking a heading scrolls it into view.
- `Escape` closes the overlay.
- State can be persisted as a simple preference after the component behavior is stable.
- No drag-to-reorder in v1.3; the outline is navigation, not an editor.

## Local Markdown links

v1.3 turns ordinary Markdown links into first-class internal navigation:

- `[Guide](guide.md)`
- `[Guide](./guide.md)`
- `[Guide](../guide.md)`
- `[Section](guide.md#Install)`
- percent-encoded spaces and Unicode paths

Clicking a local Markdown link is an explicit user action. The frontend classifies the link and sends its document-relative path to a Rust resolver. Rust canonicalizes the candidate, verifies it exists and is a supported Markdown/text file, and returns the authorized path. `App.openPath(path, heading)` remains the single tab-opening path.

Rules:

- HTTP/HTTPS remain native-confirmed external links.
- `javascript:` and unsupported schemes remain blocked.
- Document-supplied `file://` links remain blocked.
- Root-relative links are not given repository-root semantics until mdview has an explicit workspace root.
- Missing local targets show an inline/native error; they do not silently fail.
- Existing wikilinks are preserved but v1.3 does not add backlinks, graph indexing, or fuzzy workspace search.

## Local images and resource resolution

The existing Rust authorization boundary remains authoritative. v1.3 makes it capable enough for real documentation trees.

Required cases:

- `image.png`
- `./images/image.png`
- `../assets/image.png`
- spaces
- percent-encoding
- Unicode names
- supported raster formats and SVG
- missing files
- over-size files
- unsupported extensions
- blocked absolute/document-supplied privileged URI schemes

Parent-relative image references are a deliberate behavior change because both repository Markdown and mature local editors rely on them. The resolver must canonicalize the final path and keep the existing extension, file-type, and size checks. This does **not** grant Markdown script/file-system APIs: the document still only receives an image URL authorized by mdview.

Remote images remain opt-in exactly as in v1.2.5.

Reader UX:

- Responsive images never overflow the content column.
- Broken/blocked images get a visible placeholder containing alt text and a concise reason.
- Clicking a successfully loaded image opens an in-app lightbox with zoom-to-fit/full-size behavior.
- The lightbox never fetches a source that was not already authorized by the renderer policy.

## Mermaid diagrams and simple charts

Mermaid remains the diagram engine. v1.3 does not add a second charting library.

The contract is: **every valid fenced `mermaid` block supported by mdview's pinned Mermaid 11.x build is handed to Mermaid**, rather than maintaining an mdview whitelist of diagram types.

This naturally covers flowcharts, sequence/class/state/ER diagrams, timelines, Gantt, mind maps and Git graphs, plus data-oriented Mermaid diagrams such as pie charts, XY bar/line charts, radar charts, and Sankey diagrams available in the pinned version.

The existing standalone-Mermaid promotion is legacy convenience only; it is not the compatibility contract for every Mermaid grammar.

Diagram UX:

- theme-aware render
- clear bounded error surface
- zoom/fullscreen viewer for oversized diagrams
- copy source action
- horizontal/vertical overflow that does not break document layout

Security stays unchanged in principle:

- Mermaid `securityLevel: "strict"`
- remote-resource preflight when remote images are disabled
- generated SVG sanitized after rendering
- no relaxation of Tauri CSP

## Code blocks

Add syntax highlighting, but keep bundle growth controlled.

Selected dependency: `highlight.js`, imported through `highlight.js/lib/common` or an explicitly registered core subset.

Why:

- mature language coverage
- no runtime framework dependency
- supports selective imports
- smaller integration than a Shiki-based high-fidelity engine
- mdview already carries Mermaid/KaTeX, so v1.3 should not add another very large renderer bundle

Behavior:

- explicit fence language when known
- unknown/no language renders as escaped plaintext
- language badge
- copy button
- horizontal scrolling
- no code execution
- highlighted HTML still passes through mdview sanitization

## Tables

Tables should feel deliberate instead of being raw browser tables:

- GFM alignment preserved
- horizontal container for wide tables
- readable header/body borders and spacing
- no whole-page horizontal overflow
- accessible text remains selectable/copyable

No spreadsheet editing or sorting in v1.3.

## Callouts, highlights, footnotes, and math

### Callouts

Expand the existing five-type parser to the Obsidian-compatible built-in family and aliases:

- note
- abstract / summary / tldr
- info
- todo
- tip / hint / important
- success / check / done
- question / help / faq
- warning / caution / attention
- failure / fail / missing
- danger / error
- bug
- example
- quote / cite

Preserve custom titles, `+`/`-` folding, nested Markdown, and safe fallback-to-note styling for unknown types. Do not support arbitrary document-supplied CSS.

### Highlights

Support Obsidian-style `==highlighted text==` as a small inline extension, sanitized to a `mark` element.

### Footnotes

Add GFM-style `[^id]` footnotes and back-references. Prefer the maintained `marked-footnote` extension over writing a second footnote parser unless compatibility testing proves it cannot satisfy mdview's sanitizer/accessibility requirements.

### Math

Keep KaTeX. Remove global mutable render context. Preserve `trust: false` and add explicit `maxSize` and `maxExpand` limits. Support the existing `$...$` and `$$...$$` behavior; add fenced `math` compatibility only if it can be implemented without ambiguous parsing.

## Typography and reader polish

v1.3 includes a focused reader CSS pass:

- heading rhythm and anchor offset
- paragraph/list spacing
- inline code
- blockquotes
- callouts
- code frames
- tables
- images/lightbox
- Mermaid containers
- footnotes
- print behavior

Do not redesign the entire application shell in this release.

## Error model

A bad enhancement must not blank the whole document.

- Markdown parse/sanitize failure: preview-level error.
- One bad Mermaid block: block-local error; rest of document remains usable.
- Missing/blocked image: image-local placeholder.
- Unknown code language: plaintext fallback.
- Broken local Markdown link: user-action error/status; current document remains open.
- Invalid math: KaTeX error rendering, not renderer crash.

Diagnostics gathered during render should be suitable for a future diagnostics panel, but v1.3 does not build that panel.

## Performance constraints

- Parse the active document once per Markdown/security-setting change.
- Outline/search UI changes must not trigger a Markdown reparse.
- Search highlighting remains a DOM enhancement.
- Avoid importing all Highlight.js languages.
- Keep Mermaid lazy/isolated enough that code highlighting does not duplicate its weight.
- Keep the existing 20 MiB document/attachment limits.
- Add a representative "kitchen sink" fixture and a large-document regression test so the modular architecture does not accidentally introduce quadratic behavior.

## Security invariants

v1.3 must preserve:

1. Markdown is untrusted input.
2. Raw scripts, frames, objects, forms, active media, event handlers, and arbitrary document styles remain blocked.
3. Marked output is never inserted without sanitization.
4. KaTeX remains untrusted and separately sanitized/bounded.
5. Mermaid remains strict and its SVG output is sanitized.
6. External HTTP/HTTPS navigation requires explicit user action and native confirmation.
7. Remote image fetching remains disabled by default.
8. Local resources are resolved/authorized by Rust before the webview receives an asset URL.
9. Document input cannot supply privileged Tauri asset URLs.
10. Renderer extensions cannot silently widen the sanitizer allowlist; each new element/attribute requires a focused security test.

## Explicitly out of scope for v1.3

- graph view / local graph
- backlinks / unlinked mentions
- vault/workspace folder indexing
- global search
- tags/properties database
- note transclusion
- PDF/audio/video embeds
- Canvas
- plugin API
- Git UI
- rendered diff/review reports
- Agent Context Inspector
- arbitrary trusted HTML
- repository-root resolution for leading-`/` links
- frontmatter/property editing

Those remain later workspace/document-intelligence work.

## Release acceptance

v1.3 is ready only when:

- the new rendering subsystem is the only preview pipeline
- no module-level mutable render state remains
- local images handle the required path matrix
- ordinary relative Markdown links open/focus tabs and honor heading fragments
- headings have stable IDs and feed a collapsible responsive Outline
- fenced Mermaid renders representative flowchart, sequence, pie, XY chart, radar, and Sankey fixtures supported by the pinned Mermaid build
- code fences have safe syntax highlighting and copy UX
- tables, callouts, highlights, footnotes, and math have regression coverage
- one broken rich block cannot blank unrelated document content
- existing preview-sandbox tests remain green
- `pnpm test`, `pnpm typecheck`, `pnpm build`, Rust format/check/clippy all pass
- packaged-app smoke tests cover local images, local links, Outline navigation, and Mermaid on at least Linux, with Windows/macOS covered by release CI/manual checks where platform behavior differs
